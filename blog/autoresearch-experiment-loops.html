别先做 AI Scientist：从 autoresearch、AIDE 到 RD-Agent 的可控实验闭环

2026年7月31日 · 阅读需 13 分钟

如果一个团队刚开始做 AutoResearch，最诱人的目标往往是“一条 prompt 到一篇论文”：Agent 自己找文献、提假设、写代码、跑实验，最后交付 LaTeX。但整条链里最难自动化的，并不是把结果写成论文，而是回答一个更朴素的问题：这次改动真的让系统变好了吗？

模型可以为偶然波动编出解释，可以反复试探同一份 validation set，也可以无意中改坏评价脚本。只要实验结果不能独立复跑，漂亮的论文叙事就只是把不确定性包装得更完整。

因此，第一步不应是建设完整 AI Scientist，而应是建立一个可控实验闭环：人类固定问题、预算和评价边界，Agent 只在有限空间内提出改动；每次运行都留下代码、环境、日志和指标；结果由 Agent 之外的 evaluator 决定保留还是回退。它覆盖的科研阶段更少，却更接近可以审计、复现和持续改进的工程单元。

更完整的项目地图见《AutoResearch 开源项目全景》。本文只讨论实验内核：为什么 autoresearch、AIDE、RD-Agent、AutoRA 和 Curie 比“一键论文”更适合作为起点，以及怎样把它们的共同机制写成一份可执行合同。

一、先把“做研究”压缩成一份合同​

一个最小闭环可以写成：

idea -> patch -> isolated run -> evaluator -> keep / reject -> ledger -> next idea

真正决定它是否可控的，不是 Agent 数量，而是六个边界：

  1. 任务边界：基线、数据版本和要回答的问题事先确定；
  2. 可编辑面：Agent 只能修改明确列出的代码和配置；
  3. 评价边界：metric、split、预算和 evaluator 对 Agent 只读；
  4. 接受规则：主指标之外还有速度、显存、稳定性等 guardrail；
  5. 运行边界：每轮有时间、算力、费用、网络和权限上限；
  6. 证据边界：成功、失败和 crash 都进入 experiment ledger，不能只留下冠军结果。

“窄”并不等于研究价值低。它只是把开放式科研问题拆成一个暂时可机器判定的子问题。只有这个子问题运行可靠，后续的文献、假设、论文和 review 才有可信的实验地基。

二、autoresearch：极小设计为何有效​

karpathy/autoresearch 把合同压缩到了三个关键文件：人类编辑 program.md，Agent 只改 train.py，而包含数据加载、训练常量和 evaluate_bpb 的 prepare.py 不允许修改。每次训练使用固定 5 分钟 wall-clock 预算（不含启动和编译），以更低的 validation bits per byte（val_bpb）为目标。

它的 program.md 还明确规定了实验账本和状态转移：先 commit 再运行；把 commit、val_bpb、峰值显存、keep/discard/crash 和实验描述写进 results.tsv；指标改善就沿当前分支前进，持平或变差就 reset；运行超过 10 分钟按失败处理。失败没有进入最终 Git 历史，但仍留在 TSV 中，避免 Agent 重复踩坑。

这套设计有效，不是因为模型突然理解了科学方法，而是因为自由度被压低了：

  • 单文件 diff 容易人工复核；
  • 同一台机器上的固定时长实验更容易比较；
  • scalar metric 给出清晰的保留规则；
  • commit 和失败日志让循环可以回退、恢复；
  • 大约 12 次/小时的短实验允许 Agent 在夜间积累足够反馈。

它的边界也同样重要。官方实现要求单张 NVIDIA GPU，测试平台是 H100；不同硬件上的五分钟结果不可直接横比。val_bpb 只回答短预算下的验证集压缩效率，不回答长训练是否稳定、模型是否更安全、改动是否新颖。反复围绕同一 validation metric 搜索还会产生适应性过拟合：试验次数越多，最好的单次结果越可能包含噪声。

还有一个容易忽略的工程事实：program.md 中的“不得修改 prepare.py”首先是一条 Agent 指令，不天然等于安全边界。真实部署应把 evaluator 放到独立 runner，把评价代码和隐藏数据只读挂载，校验文件 hash，并让生成代码拿不到修改权限。否则所谓“不可变 evaluator”只是 prompt 里的君子协定。

三、AIDE：从线性爬山变成可检查的搜索树​

AIDE 保留了“代码—运行—指标”的核心，但不再只沿一条分支前进。用户提供数据目录、自然语言 goal 和 metric；每份候选 Python 脚本成为 solution tree 的一个节点，LLM 生成 draft、debug 或 improvement patch 作为子节点，再由 metric feedback 引导后续搜索。当前仓库默认 20 个 improvement steps、每步 5 个 drafts，并输出 best_solution.py 和完整的 tree_plot.html。

树搜索的价值不是“尝试更多”这么简单。线性循环一旦接受局部改进，后续实验都建立在这条路径上；AIDE 可以保留不同建模路线、修复有潜力但暂时 crash 的节点，也能回看一个高分解法从哪条 patch 链演化而来。它因此很适合作为 ML 代码搜索内核：AIDE 作为公开基线进入了 MLE-bench，AI Scientist v2 也明确说明其 tree-search component 建立在 AIDE 之上。

但树越大，评价风险也会被放大。几十个节点反复读取同一个 validation score，本质上是在对 validation set 做多重比较；如果候选脚本还能接触标签、split 逻辑或评分代码，Agent 甚至可能通过数据泄漏而不是建模获得高分。AIDE 给出了搜索机制，不会自动替团队设计可信 benchmark。生产接入时仍要把开发集搜索、锁定的 shadow evaluation 和最终 test 分开，最终评分由工作区之外的 runner 完成。

AIDE 的主要产物是最佳代码和搜索树，不是已经成立的科学 claim。这个限制反而使它角色清楚：它可以嵌入更大的系统，但不应被误称为完整 AI Scientist。

四、RD-Agent：把“想法”和“实现”拆开​

microsoft/RD-Agent 把闭环扩大到数据驱动研发，并明确区分两个角色：Research（R）提出 idea，Development（D）把 idea 实现为可运行代码，再从实验反馈中进入下一轮。项目提供量化因子与模型、Kaggle/通用 data science、论文模型复现、LLM fine-tuning 等场景；多数场景在 Linux 上通过 Docker 执行，并提供 PyPI 包、health check、运行日志和可视化界面。

R/D 分工比“一个 Agent 既提案又证明自己正确”更容易插入检查点。团队可以分别替换 proposer、coder 和 evaluator，也可以让昂贵模型负责研究决策、较便宜模型负责实现。项目 README 发布的 MLE-bench 结果使用 5 或 6 个 seeds，并提供详细 runs；这比展示一次最佳成绩更有证据价值，但仍应区分项目自报结果与外部独立复现。

RD-Agent 的优势来自 scenario，而不是无边界通用性。量化、Kaggle 和 fine-tuning 各自有数据、runner、反馈和停止条件；接入成本也高于 AIDE，需要维护 Docker、数据权限、模型与 embedding 配置以及场景专用 evaluator。R 和 D 的分离同样不等于评价独立：最终 benchmark 必须由第三个、只读的执行边界掌握，不能让提出 idea 的模型同时决定它是否成功。

五、AutoRA 与 Curie：实验不只等于改 ML 代码​

AutoRA 展示了另一种闭环。它最初面向行为与脑科学，把流程拆成 experimentalist、experiment runner 和 theorist，并用 StandardState 在模块间传递 conditions、experiment_data 和 models。experimentalist 选择下一批条件，runner 收集观测，theorist 根据累积数据更新模型，再进入下一轮。这里的中心不是 LLM，而是可持续更新的 empirical state；模块可以使用传统 Bayesian Machine Scientist，也可以接入 Agent。

Curie 则覆盖 hypothesis、实现、执行、分析和 Markdown 报告，提供 verification modules、生成代码、结果文件和 EXP-Bench，并允许用户带入 starter code 与 dataset。实验层依赖 Docker，ML 训练建议使用 GPU。它比 AIDE 更接近完整实验 workflow，但报告仍不是论文有效性的证明；而且截至本次 2026-07-31 快照，仓库最近 HEAD 停在 2025-09，活跃度应与功能清单分开判断。

这两个项目提醒我们：闭环的核心接口应是“状态—行动—观测—更新”，不必强行写成多 Agent 对话。对于真实仪器、仿真器或领域数据，最难的工作往往是实现可信 runner、校准观测误差和定义停止规则，而不是再增加一个会讨论的角色。

这五个项目也不应按“谁更自主”排成一条榜单。已有单训练脚本、一个稳定 scalar metric 时，可以先复用 autoresearch 的线性合同；面对给定数据集、希望并行保留多条建模路线时，AIDE 的搜索树更合适；需要把提案、实现和多个行业场景接入统一框架时，再考虑 RD-Agent。若研究对象包含真实条件选择和观测采集，AutoRA 的 state loop 比代码排行榜更自然；若目标是从问题推进到实验报告，Curie 可作为 workflow 参考。选型依据应是 evaluator 和 runner 是否已经存在，而不是项目名字离“AI Scientist”有多近。

六、指标会被优化，也会被钻空子​

一旦 Agent 能进行几十到上百次尝试，评价设计就从附属配置变成系统的信任根。

失败模式表面现象最低控制
Goodhart主指标上升，延迟、显存或鲁棒性恶化一个主指标加硬性 guardrails；违规结果直接拒绝
evaluator tampering分数异常跃升，评价脚本或 split 同时变化evaluator 独立进程、只读挂载、hash 校验、隐藏标签
validation overfitting开发分数持续上升，锁定集不复现dev 用于搜索，shadow set 用于入围复验，test 不进入循环
随机波动单 seed 赢很多，换 seed 即消失先低成本筛选，再对少量候选做预注册的多 seed 复跑
环境漂移后期实验因依赖、GPU 或数据变化不可比固定 image digest、依赖 lock、数据版本、GPU/驱动与预算
幸存者偏差只保存最佳代码，看不到试过什么所有 keep、reject、crash、timeout 都写入只追加、不可改写的 ledger

“固定预算”也必须写清固定的是什么。固定 wall-clock 会奖励更适合当前 GPU、kernel 和编译路径的方案，固定 tokens 或 epochs 则更接近样本效率比较；二者回答的不是同一个问题。若目标是线上吞吐，机器相关的五分钟优化完全合理；若目标是算法结论，就应同时报告计算量、数据量和跨硬件复验，不能把平台特化结果泛化成普遍进步。

多 seed 也不能只报平均值。应先用基线重复运行估计方差，预先规定 seed 数、最小有意义 effect size 和接受阈值；候选进入确认阶段后，再报告均值、离散程度和失败率。否则团队可以在看到结果后继续补 seed，直到统计结论看起来顺眼。

experiment ledger 至少要能回答：这个 run 从哪个 parent/idea 来，改了哪个 commit，使用哪份数据、evaluator 和容器，在哪种硬件上以哪些 seeds 跑了多久，主指标和 guardrails 是什么，为什么被接受或拒绝，原始日志、模型、图表与费用在哪里。Git 只适合保存代码状态，不能替代完整实验账本。

七、一份可以直接试跑的最小合同​

下面不是某个框架的现成配置，而是一份适合改成团队 schema 的示例：

task: improve model X on dataset Y
baseline_commit: <sha>
editable_paths: [src/model.py, configs/model.yaml]
read_only_to_agent: [runner/client.py]
hidden_from_agent: [evaluator/, data/shadow/]
sandbox:
  network: deny
  secrets: none

search:
  split: dev_v1
  objective: auroc
  max_trials: 30
  wall_time_per_trial: 15m
  gpu_per_trial: 1
  seed: 11

guardrails:
  latency_p95_ms: "<= 40"
  peak_vram_gb: "<= 16"
  crash_rate: "== 0"

confirm:
  runner: independent
  split: shadow_v1
  seeds: [11, 23, 37, 51, 71]
  shortlist: 3
accept:
  mean_delta: ">= 0.005"
  ci95_lower_bound: "> 0"
  no_guardrail_regression: true
ledger: artifacts/experiments.jsonl
stop: [budget_exhausted, 10_trials_without_gain, sandbox_violation]

推荐的上线顺序是：先手工跑通 baseline 并测量方差；再让 Agent 在 dev split 上做 20–50 次短实验；只把少量候选交给独立 runner 多 seed 复验；人工检查 diff、失败路径和成本后才合并。等这条 agent -> job -> result -> decision -> ledger 链能在中断后恢复、在干净环境复跑，再接文献检索、claim-to-evidence 和 LaTeX。

这也是为什么完整 AI Scientist 应当最后评估，而不是最先建设。端到端系统可以负责编排，但不能成为自己的信任根。关于从实验闭环扩展到论文管线时新增的许可证、引用和责任问题，可继续看《一条 Prompt 到一篇论文？》；关于 sandbox、GPU queue、provenance 与独立 reviewer，则见《AutoResearch 工程底座》。

真正值得自动化的，不是“生成一篇看起来成立的 PDF”，而是让每个 idea、patch、失败、数字和接受决定都可回放、可质疑、可推翻。一个边界清楚的窄闭环，往往比一个会写论文的全能 Agent 更接近科学方法。
