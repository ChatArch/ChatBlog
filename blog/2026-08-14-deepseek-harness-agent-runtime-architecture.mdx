DeepSeek Harness 是 DeepSeek 开源的 agent runtime。它把模型放进一个 workspace，让模型带着上下文完成任务：读项目、调用工具、改文件、执行命令、留下过程记录。

普通 Chat UI 围绕问答组织界面。Harness 围绕一次 agent 行动组织运行时：上下文、工具、执行、日志和界面都在同一条链路里。

![DeepSeek Harness Agent Runtime 架构图](/img/deepseek-harness/agent-runtime-architecture.svg)

这张图从上到下看：上半部分是启动入口和插件组合，下半部分是一轮 turn/step 的行动路径。读源码时先沿着这条路径走，再回头看各包的职责。

官方仓库是 `deepseek-ai/deepseek-harness`，运行包是 `@deepseek-ai/dsh`。[1][2] README 直接把架构落在一句话上：`Everything is a Plugin`，底层由 Cordis 驱动。[1]

读它可以从一次 agent turn 开始：启动配置拼出插件树，插件贡献 prompt 和 tools，agent loop 调模型并执行工具，session/event log 留下过程，Web UI 从日志里投影出可观察界面。

## 先看一轮任务怎样流动

一轮任务从用户输入开始，随后进入运行时组合出来的能力链路。

| 阶段 | 发生了什么 | 读源码时看哪里 |
| --- | --- | --- |
| 启动形态 | profile、bundle、patch 组合出本次运行的插件树 | `packages/boot/app-boot` |
| 能力装配 | Cordis 挂出 service、event、effect 和 fiber lifecycle | `docs/architecture.md` |
| 模型上下文 | system prompt registry 汇总身份、上下文、工具 schema、插件 section | `packages/core/system-prompt` |
| 工具执行 | tool registry 经过审批、guard、execute、post-process、result notification | `packages/core/tools` |
| 过程记录 | assistant chunk、tool call、tool result、turn/step 边界进入 session event | cookbook 和 session 相关包 |
| 界面呈现 | Web UI 订阅事件，把过程画给人看 | `client` 和 extension cookbook |

这张表比目录树更有用。目录告诉你文件在哪里，任务链路告诉你这些包为什么需要一起工作。

## 启动层：profile / bundle / patch 决定 runtime 形态

`@deepseek-ai/dsh-app-boot` 的 README 把启动机制讲得很清楚：profile 位于 `$DSH_HOME/profiles/<name>`，里面有 package 依赖和 `dsh.profile` manifest；bundle 是带 `dsh.bundle.patch` 的 npm package；用户还能通过 profile/home 级别的 `cordis.patch.yml` 和命令行 `--patch` 叠加配置。[4]

这些配置描述的是运行拓扑。

| 入口 | 作用 |
| --- | --- |
| `web` profile | 启动 Web UI、host API、浏览器侧协作体验 |
| `headless` profile | 跑一次 CLI agent task，适合自动化和 smoke test |
| `base` bundle | 提供公共 agent 能力，供不同 profile 复用 |
| 用户 patch | 插入本地插件、覆盖配置、调整插件树 |

`renderConfigDump()` 使用同一套 patch 逻辑渲染最终配置，`watchUserPatches()` 负责监听 patch 变更并重新应用。[4] 读 Harness 时，最先要问的是：当前 profile 最终拼出了哪棵插件树？这比逐项背配置名更接近真实运行。

## Cordis 层：插件拥有生命周期

官方架构文档把 Harness 建在 Cordis container、service registry、typed events、effects 和 fiber lifecycle 上。[3]

直白讲，插件会活在运行时里。插件可以提供 `tools`、`systemPrompt`、`agents`、`sessions` 这类 service；可以监听 `session/event`、`tools/pre-execute`、`system-prompt/assemble` 这类 event；还可以注册带 disposer 的 effect。插件随 fiber mount，能力随 fiber dispose 撤销。热重载、配置重组和能力卸载都依赖这套生命周期。[3][7]

官方 extension cookbook 里的工具插件、hook 插件、UI 插件、protocol driver 都走这个模型。[7]

几个例子能把 Cordis 的意义讲清楚：permission gate 插件监听 `tools/pre-execute`，MCP 插件发现外部工具后注册到 `ctx.tools`，UI 插件监听 `session/event` 后展示新投影。agent loop 面向稳定 seam，具体能力由插件挂载。

DeepSeek Harness README 链接的 Cordis 论文 _A Programming Paradigm for Spatiotemporal Composability_ 也在解释这个方向：动态系统需要管理组件安装、撤销和依赖变化。[1]

## Prompt 层：模型看到的是当前 runtime 的投影

`dsh-system-prompt` 把 prompt 做成 assembly registry：插件贡献有顺序的 sections、tool schemas 和变量，agent loop 每一步都组装当前模型上下文。[6]

模型看到的内容来自几类来源：Harness identity、部署 persona、workspace/AGENTS 等上下文、插件贡献的 prompt section、当前可见 tool schema、scoped override。它们按规则汇总成当前 step 的 prompt。

几个 API 决定了 prompt 的运行时性质：[6]

| API / event | 作用 |
| --- | --- |
| `ctx.systemPrompt.section()` | 插件贡献具名、有顺序的 prompt section |
| section scope | agent-scoped section 可以覆盖 global section |
| `ctx.systemPrompt.tools()` | 插件贡献模型可见 tool schema |
| `system-prompt/assemble` | waterfall event，插件可协作修改最终 assembly |
| 变量插值报错 | 坏模板直接失败，避免静默污染 prompt |

[实践篇](/blog/deepseek-harness-webui-plugin-practice)里，我就用了这个 seam：本地 ESM 插件调用 `ctx.systemPrompt.section()` 注入 marker，headless 模型能看到并回显 marker。这个结果说明插件已经进入模型上下文。

## Tools 层：工具调用有可检查的执行管线

`dsh-tools` 把自己定义为 tool registry and execution pipeline。工具插件通过 `ctx.tools.register()` 注册 schema 和 executor，agent loop 调工具时经过固定管线。[5]

| 管线位置 | 适合放什么 |
| --- | --- |
| `tools/pre-execute` | 审批、拒绝、用户确认、权限检查 |
| monotonic guard | 产生后续 listener 无法反转的拒绝 |
| `tools/execute` | 真实 dispatch，可加 deadline、retry、metrics |
| `tools/post-execute` | 检查、替换或规范化结果 |
| finalize / render | 把 canonical JSON value 渲染成模型可读内容 |
| result notification | 观察最终 immutable outcome |

这个设计让一次工具调用同时服务几类对象：模型需要可读结果，UI 需要状态，日志需要事实，安全策略需要拦截点，调试者需要知道失败发生在哪一段。

工具定义也有契约。`defineTool()` 声明参数 schema、输出 schema 和 render 逻辑；成功结果先是 canonical JSON value，再渲染成模型可读内容。[5][8]

## Session/event log 层：过程本身成为产物

官方 extension cookbook 的 UI 插件例子监听 `session/event`。assistant streaming chunk 对应 `assistant/chunk`，工具活动和 turn/step 边界也进入事件流。[7]

这让 Web UI、replay、debug 共用一批事实。coding agent 的价值常常在过程里：读了哪些文件，改了哪些 diff，跑了什么命令，失败后怎样修。Harness 把这些过程写进 event log，最终回答只是事件流的一个投影。

## 安全边界跟 runtime 一起看

Harness 能读写文件、执行 shell、调用 Web、启动子 agent。部署口径要按高权限本地服务来设计。

我们的实践里碰到过一个典型问题：Web UI 通过公网入口访问 host API 时，反代层的 Host / Origin / forwarded header 组合不一致，目录 API 被 request trust fence 拒绝。表现是 `host.listDirectory` 返回 403。这个错误说明安全边界已经在工作。

部署时至少守住几条线：Harness 进程监听本机或受控内网；外层入口提供身份认证和访问控制；反代头和 public host 保持一致；公开文章、日志、截图不出现 live service URL、内部主机名、私有路径或凭据；高风险工具进入 approval 或 sandbox 路径。

## 它和现有 coding agent 工具的关系

| 工具 | 适合做什么 | Harness 的位置 |
| --- | --- | --- |
| Claude Code / Codex CLI | 直接进仓库写代码、跑测试 | 成熟 coding-agent 产品形态 |
| 普通 Chat UI | 问答、文件上传、轻量任务 | 隐藏大部分 runtime 结构 |
| Hermes Agent | 多平台投递、长期记忆、skills、调度、本机/远端工具 | 跨平台 agent 操作系统 |
| DeepSeek Harness | 研究和搭建 coding-agent runtime | 公开 UI、profile、plugin、tools、event log 和安全 seam |

DeepSeek Harness 把现代 coding agent runtime 的骨架放在公开仓库里。当前 npm `@deepseek-ai/dsh` 的 latest 是 `0.1.0-rc.6`；我读到的源码快照里很多 package 仍是 `0.1.0-rc.5`。[2] 读源码、跑 npm 包、写插件时要锁住版本，避免把不同快照混在一起判断。

## 结论

DeepSeek Harness 把 agent runtime 的硬问题放在同一个工程里：启动形态由 profile/bundle/patch 管，组合模型由 Cordis plugin tree 管，模型上下文由 system prompt assembly 管，工具行动由 registry 和 execution pipeline 管，过程由 session/event log 管，风险由 approval、sandbox 和 trust fence 管。

它仍处在 developer preview。研究 runtime、写小插件、理解 agent 平台拆分方式，很合适；开放公网服务和生产承载，需要更完整的认证、沙箱和运维边界。

实践篇继续把这条链路跑了一遍：部署 Harness，让 Web UI agent 修一个小仓库里的 bug，再用最小插件证明 `--patch` 和 `ctx.systemPrompt.section()` 进入模型上下文。
