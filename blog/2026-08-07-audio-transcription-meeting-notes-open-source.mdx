# 录音转写与会议笔记自建选型：网页录音入口 + API 转写

这次选型的目标不是“让 bot 加入 Zoom / Google Meet / Teams”，也不是直接采购一个纯 SaaS 转写产品。真正需求是：**自建一个网页或软件入口，用户在网页里点击录音，系统开始记录语音、实时或准实时转写，并用 LLM 生成摘要、行动项、决策和分析**。

换句话说，产品入口要自建，ASR 和 LLM 能力通过 API 接入；不要自建 Whisper / diarization / summary 全流程，也不要把 meeting bot 当主线。

<!-- truncate -->

:::tip 最终推荐
**生产路线：OpenTranscribe API-lite / cloud-ASR 后台 + 自建 Web/PWA 录音入口。**

**最快验证：先 fork / 参考 Cognium Meet。** 它已经有 Chrome extension + local API、tab audio / mic 录音、OpenAI 转写、meeting notes 和 Ask。若必须是“普通网页点录音”而不是浏览器插件，则保留它的 API/笔记思路，自己补一层 Web/PWA recorder。
:::

:::info 证据口径
本文快照日期为 **2026-08-07**。候选来自 GitHub 仓库、README、官方文档、license/release 状态和源码/配置关键字。本文只把外部 ASR / LLM API 当作能力层，不把 Deepgram、AssemblyAI、OpenAI、DashScope、腾讯云、讯飞等 API 厂商当作“方案本身”。
:::

## 需求边界先写清楚

这类需求有三个硬条件：

| 条件 | 含义 | 排除什么 |
| --- | --- | --- |
| **自建产品入口** | 用户打开我们自己的网页/系统，点击录音，看到 transcript 和会议笔记 | 直接把用户导到第三方 SaaS |
| **通过 API 接入模型能力** | ASR、说话人、摘要、分析可以接外部 API provider | 自己长期维护本地 ASR/GPU/模型 pipeline |
| **常规会议/想法笔记录音** | 线下会议、微信会议外放/电脑声音、访谈、个人口述笔记、浏览器会议 | 会议 bot 自动入会作为主线 |

因此，方案应该按下面这条链路设计：

```text
Web/PWA 录音入口
  → audio chunk / file upload
  → STT adapter（统一 provider 接口）
  → ASR API：讯飞 / 腾讯云 / DashScope / Deepgram / AssemblyAI / OpenAI 等
  → Transcript store + speaker/timestamp metadata
  → LLM notes：摘要、行动项、决策、问题、分析、自定义模板
  → Feishu / Markdown / ChatArch workspace / 搜索归档
```

## 直接结论：不要找一个“万能现成项目”

完全贴合“自建网页点录音 + API 转写 + 会议笔记 + 可定制”的 GitHub 项目并不多。最靠谱的路线不是押一个项目，而是拆成两个层：

1. **网页录音入口层**：自己做薄一点，或者先参考 Cognium Meet。
2. **转写/归档/笔记后台层**：优先看 OpenTranscribe 的 cloud-ASR / API-lite 能力。

这样不会被某个开源项目的 UI、模型、会议平台或本地 GPU 绑死。

## 候选排序

| 排名 | 候选 | 用法 | 为什么 |
| --- | --- | --- | --- |
| 1 | **OpenTranscribe + 自建 Web/PWA recorder** | 生产主线 | OpenTranscribe 已经有 Web 应用、上传/导入、Cloud ASR providers、LLM providers、custom prompts、搜索、队列和团队媒体库方向；我们只需要补一个更符合自己场景的网页录音入口。 |
| 2 | **Cognium Meet** | 最快原型 / 可 fork 参考 | 它最接近“浏览器录音 + API 转写 + notes + Ask”：Chrome extension 录 tab audio + 可选 mic，local API 上传音频，OpenAI `whisper-1` / diarized transcription，生成 notes/action items/decisions/open questions。 |
| 3 | **Scriberr** | 录音文件后台备选 | 有 PWA、录音、notes、chat with audio、folder watcher 和 API，但主线更偏本地模型；如果要走纯 API-first，需要额外改 cloud-ASR adapter。 |
| 4 | **Pikabaka / screenpipe** | 桌面采集体验参考 | 对微信会议、桌面系统音频 + 麦克风很有启发，但它们更像桌面 app / 个人工作记忆，不是“网页点录音”的后台主线。 |
| 5 | **Vexa / Attendee** | 只在需要 bot 入会时再看 | 这类是 meeting bot API，不适合当前“网页录音/旁路录音”主场景。 |

## 第一推荐：OpenTranscribe 做后台，自己补网页录音入口

Repo: [attevon-llc/OpenTranscribe](https://github.com/attevon-llc/OpenTranscribe)

OpenTranscribe 是这批项目里最接近“自建后台产品”的候选。它的 README 明确列出：

- Cloud ASR providers：Deepgram、AssemblyAI、OpenAI Whisper API、Google、AWS Transcribe、Azure、Speechmatics、Gladia 等；
- API-Lite deployment：`DEPLOYMENT_MODE=lite`，用于 cloud-ASR-only 部署，避免本地 GPU；
- Multi-provider LLM：OpenAI、Claude、Ollama、OpenRouter、vLLM 等；
- Custom summary formats / custom AI prompts；
- 上传、队列、搜索、集合、RBAC、watch sources、S3/SMB/local folder 自动导入；
- transcript、speaker、summary、topic、collection 等媒体库能力。

![OpenTranscribe official workflow](/img/audio-transcription-meeting-notes/opentranscribe-workflow.gif)

*OpenTranscribe 官方 workflow GIF：展示从 login、upload、process、transcribe 到 speaker identification 和 AI tags/collections 的链路。来源：OpenTranscribe 官方仓库。*

它的问题是：**它更像后台和媒体库，不是一个极简“点录音开始”的网页录音器。**

所以推荐架构是：

```text
我们的 Web/PWA recorder
  → 录音分片 / 完整音频上传
  → OpenTranscribe API-lite / cloud-ASR queue
  → Cloud ASR provider
  → OpenTranscribe transcript + summary/custom prompts
  → ChatArch / Feishu / Markdown 输出
```

这个路线最符合三个要求：自建入口、API 能力、可定制会议笔记。

### 什么时候不选 OpenTranscribe

如果目标只是两三个人先试一个最小 demo，OpenTranscribe 可能偏重。它涉及媒体库、权限、队列、存储和多个后台组件。此时可以先用 Cognium Meet 或自己写最小 recorder API 验证。

## 最快验证：Cognium Meet

Repo: [cogniumhq/cognium-meet](https://github.com/cogniumhq/cognium-meet)

Cognium Meet 的 README 直接写明：

- Chrome extension + local API；
- 录制 browser tab audio，可选 microphone，支持 mixed 或 dual-track `You / Others`；
- 通过 OpenAI `whisper-1` 或 diarized transcription 转写；
- 生成 meeting notes：summary、action items、decisions、open questions；
- Ask：可以对单个会议或历史会议问答；
- API 提供 `/v1/recordings`、transcript、notes、Ask 等接口；
- 可以让用户在 extension settings 里 BYOK，也可以 server fallback。

它非常贴近“网页/浏览器侧录音 + API 转写 + 会议笔记”的原型。

但它不是完美答案：

| 点 | 判断 |
| --- | --- |
| 产品入口 | Chrome extension，不是普通网页按钮 |
| 音频来源 | 强在 browser tab audio + mic；对微信桌面客户端不直接适用 |
| ASR provider | 默认 OpenAI；要接讯飞/腾讯/DashScope 需要改 provider adapter |
| 适用方式 | **最适合 fork 做 PoC，或借它的 extension/API/notes 数据模型** |

如果我们可以接受 Chrome extension，它就是最快 demo。若用户必须打开一个普通网页点击录音，仍建议自己做 Web/PWA recorder，把 Cognium Meet 的 API 设计和 notes workflow 拿来参考。

## Web/PWA recorder 应该自己做薄层

这层不要做复杂。第一版只需要：

1. 浏览器 `MediaRecorder` 获取麦克风音频；
2. 可选：分片上传，避免长会议中断；
3. 录音中展示 realtime / near-realtime transcript；
4. 会议结束后调用 LLM 生成 notes；
5. 支持自定义模板：周会、访谈、项目讨论、想法整理、销售访谈、技术方案评审；
6. 保留原始音频、transcript、speaker/timestamp、summary JSON；
7. 输出 Markdown / Feishu 文档 / ChatArch workspace。

这层自研的好处是产品体验完全受控：按钮、录音权限、暂停/继续、断线恢复、模板选择、隐私提示、保存位置、团队权限都可以按自己的工作流设计。

## ASR / LLM provider 只是插件，不是方案

API provider 只放在 backend adapter 层：

| 能力 | Provider 候选 | 选型标准 |
| --- | --- | --- |
| 中文实时/准实时 ASR | 讯飞、腾讯云 ASR、DashScope Paraformer | 中文会议准确率、热词/自定义词、长音频稳定性、国内链路 |
| 多语种/开发者体验 | Deepgram、AssemblyAI、Gladia、Speechmatics、OpenAI | diarization、timestamp、标点、流式延迟、SDK/价格 |
| 笔记总结/分析 | Qwen、GPT、Claude、Gemini、OpenAI-compatible gateway | 自定义模板、结构化 JSON、长 transcript 处理、稳定性 |

工程上建议做一个内部统一接口：

```text
POST /api/recordings
POST /api/recordings/:id/chunks
POST /api/recordings/:id/transcribe
POST /api/recordings/:id/notes
GET  /api/recordings/:id/transcript
GET  /api/recordings/:id/notes.md
```

provider 可以随时替换，但用户面对的是我们自己的网页产品。

## 为什么不是 Scriberr / Whishper / Vexa

### Scriberr

Repo: [rishikanthc/Scriberr](https://github.com/rishikanthc/Scriberr)

Scriberr 有不少产品层能力：PWA、录音、笔记、chat with audio、folder watcher、API、speaker detection、summary。它适合“录音文件进来，后台处理和问答”。

但它主线仍偏本地模型。如果我们明确“不自建 ASR 模型，只通过 API 接入”，Scriberr 需要先做 cloud-ASR adapter 才能成为主线。因此它排在 OpenTranscribe 之后。

![Scriberr official recording library screenshot](/img/audio-transcription-meeting-notes/scriberr-hero.png)

*官方截图展示了 Scriberr 的录音列表和移动端 PWA 体验。来源：Scriberr 官方仓库。*

### Whishper

Repo: [pluja/whishper](https://github.com/pluja/whishper)

Whishper 是字幕/媒体转写套件，适合视频、课程、访谈、YouTube、SRT/VTT 编辑。它不是会议笔记产品主线，也不适合“网页录音 + API provider + 自定义纪要模板”的第一阶段。

### Vexa / Attendee / Recall.ai

这些是 meeting bot / meeting API 方向，解决“系统自己加入 Zoom/Meet/Teams 会议”的问题。当前需求是不让 bot 入会，而是网页录音，所以它们不进入主推荐。

## 最小落地计划

### 第 0 步：一周内验证

- fork / 跑 Cognium Meet，看它的录音、转写、notes、Ask 是否满足原型；
- 同时用一个最小 Web/PWA recorder 验证网页点录音、分片上传、生成 transcript；
- ASR provider 先接一个国内中文候选和一个国际候选，统一成 adapter。

### 第 1 步：产品化

- 用 OpenTranscribe API-lite / cloud-ASR-only 部署做后台候选；
- 接自建 Web/PWA recorder；
- 增加自定义会议模板和 summary JSON schema；
- 输出 Feishu / Markdown；
- 加权限、团队空间、录音保留策略。

### 第 2 步：体验增强

- 支持实时字幕；
- 支持边录边摘要；
- 支持会后 Ask；
- 支持术语词表、人名、项目名、客户名；
- 支持“想法笔记”模板，不只会议模板。

## 最终判断

如果现在只选一个主方案，我会选：

```text
OpenTranscribe API-lite / cloud-ASR 后台
  + 自建 Web/PWA recorder
  + Cognium Meet 作为最快原型和代码参考
```

这比“直接上 Vexa”更贴近需求，也比“只列 ASR API 厂商”更像一个真正可自建的产品。
