我这次想验证一件具体的事：DeepSeek Harness 能否在 workspace 里完成一次受控代码修改，并让树外插件进入模型上下文。

实测结果：`@deepseek-ai/dsh@0.1.0-rc.6` 在 Node `v22.19.0` 下正常启动；headless 返回 `OK`；Web UI agent 修复了一个小 JS 仓库里的百分比计算 bug，`npm test` 通过；本地 Cordis 插件通过 `--patch` 插入 profile，模型读到了插件注入的 marker，宿主侧也读到了插件执行留下的 marker 文件。

## 验收标准

网页能打开，说明前端资源能加载。coding-agent runtime 还要验收行动链路。

| 检查 | 合格信号 | 这一步排除什么问题 |
| --- | --- | --- |
| headless smoke | 模型精确返回 `OK` | provider、profile boot、一次性 agent loop 不通 |
| Web UI workspace | 页面能选择受控 workspace，host API 返回 200 | 浏览器连接、host API、反代 header、workspace 权限异常 |
| 小仓库修 bug | agent 修改源文件，测试通过，结果文件可回读 | 工具链只是展示、没有真实读改测 |
| 插件 patch | 本地 ESM 插件被加载，prompt marker 被模型看到 | profile overlay 没进入 Cordis 插件树 |
| 宿主 marker | marker 文件存在并包含验证值 | 插件 `apply()` 没执行，只有模型侧幻觉 |
| 安全口径 | 服务入口、内部路径、凭据都不进入公开材料 | 高权限工具被误当普通 Web demo |

后面的实践按这张表推进。

## 环境选择：Node 版本先定住

目标机器的系统 Node 是 Node 10 系列，无法支撑现代 TypeScript/Node 工程。Node 24 在当时环境里触发 native dependency build / runtime 兼容问题；Node `v22.19.0` 路线稳定。

部署方式保持隔离：独立 Harness home、独立 npm cache、独立 workspace。密钥不写进文章、报告、截图或仓库。Web 进程先监听本机地址，对外访问交给反代和访问控制。

这个项目还处在 preview 阶段。检索时 npm `@deepseek-ai/dsh` 是 `0.1.0-rc.6`，公开源码快照里不少 package 仍显示 `0.1.0-rc.5`。[2] 排错时要同时记录“跑的包版本”和“读的源码快照”。

## Headless smoke：先确认 agent loop 通了

最小命令只有一条：

```bash
dsh --profile headless "Reply with exactly OK."
```

返回：

```text
OK
```

这一步看起来小，却很省时间。它确认 provider、profile boot 和一次性 agent loop 已经工作。后面 Web UI 出问题时，排查范围就集中到浏览器、host API、反代和 workspace。

## Web UI：403 是安全边界在拦截

Web UI 打开后，我看四个可回读信号：页面 title 是 `DeepSeek Harness`；能看到会话、工作区、设置入口；workspace 请求能到 host API；本地 health 返回 200。

第一次选择 workspace 时，浏览器侧拿到这个错误：

```text
transport failure for /api/host.listDirectory: HTTP 403
```

根因在反代链路。浏览器发起 host API 请求，后端会检查 Host、Origin 和 forwarded header。反代层当时没有保持 public host 形态一致，触发 request trust fence。

修复后，我只保留脱敏形态作为公开证据：`host.listDirectory` envelope 返回 `status: 200`，`ok: true`，并能看到 entries count。文章里不展示路径、主机名和目录名。

这一步给了一个很实际的部署判断：反代配置属于 runtime 安全边界。Harness 的 Web UI 背后连着 workspace、文件系统和命令执行能力，public host、认证、访问控制和 forwarded header 都要进验收。

## Web UI 任务：让 agent 修一个小 bug

我准备了一个小 JS workspace，文件很少：`package.json`、`src/quote.js`、`test/quote.test.js`。业务函数 `estimateQuote` 故意写错：`discountPercent` 和 `taxPercent` 是百分比数值，`10` 表示 10%，`5` 表示 5%；错误实现把它们当成直接倍率。

给 agent 的任务没有花哨内容，只要求它完成四件事：读 `package.json`、源文件和测试；修复百分比计算；运行 `npm test`；写 `PRACTICE_RESULT.md` 记录改动和测试摘要。

| 观察点 | 回读结果 |
| --- | --- |
| 源码修改 | `src/quote.js` 把百分比输入转换成比例计算 |
| 修复公式 | `discount = subtotal * discountPercent / 100`，`tax = discountedSubtotal * taxPercent / 100` |
| 测试命令 | `npm test` 由 agent 执行 |
| 测试输出 | `PASS applies discountPercent and taxPercent as percentages`；`PASS rejects negative hours or rates` |
| 结果文件 | `PRACTICE_RESULT.md` 记录改动原因和测试摘要 |

结果文件的公开摘录只保留事实形态：修复点是百分比换算，测试命令是 `npm test`，两条测试用例都通过。任务规模很小，验收面完整：读文件、理解测试、改源文件、跑命令、根据结果继续、写结果报告。这个过程比 hello world 更能说明 Web UI 的工具链真实工作。

## 插件验证：把树外能力插进 runtime

Web UI 修 bug 验证了内置能力。Harness 的架构重点还包括插件化，所以还要验证树外插件能进入 runtime。

我做了一个最小 Cordis 插件，职责很窄：

| 插件动作 | 验证方式 |
| --- | --- |
| `apply(ctx)` 执行时写 marker 文件 | 宿主侧读取 marker 文件，确认包含 `PLUGIN_EXTENSION_VERIFIED=1` |
| 调用 `ctx.systemPrompt.section()` 注入 prompt marker | headless 模型返回 `DSH_PRACTICE_PLUGIN_ACTIVE` |

插件通过本地 ESM 文件加载，没有发布 npm 包。`app-boot` 文档说明，用户 patch layer 可以用 `insert` 添加 entries；profile boot 会把 bundle patch、profile patch、home patch 和 overlay patch 合成最终插件树。[4]

patch 的公开形态只保留结构，不放真实绝对路径：

| 字段 | 含义 |
| --- | --- |
| `id: practice-plugin-marker` | 插件 entry 的稳定 id |
| `name: file://.../dsh-practice-plugin.mjs` | 本地 ESM 插件 URL |
| `marker` | 注入 prompt 的公开 marker 文本 |
| `markerPath` | 宿主侧验证文件，公开时脱敏 |
| `promptSectionName` / `promptOrder` | system prompt section 的名字和顺序 |

这里踩过一个实际坑：相对路径插件在当时启动方式下不稳定。改成明确 `file://` URL 后加载成功。公开文章不放真实路径，复现时要留意插件 specifier 的解析基准。

验证时，我让模型返回实践 marker。模型侧证据和宿主侧证据分开看：

| 证据 | 来源 | 说明 |
| --- | --- | --- |
| `DSH_PRACTICE_PLUGIN_ACTIVE` | 模型输出 | prompt section 已进入模型上下文 |
| `PLUGIN_EXTENSION_VERIFIED=1` | 宿主 marker 文件 | 插件 `apply()` 执行，配置检查通过 |

宿主 marker 文件只写一行公开验证值：`PLUGIN_EXTENSION_VERIFIED=1`。模型侧 marker 和宿主侧 marker 分开记录，避免把“模型复述了 prompt”误当成“插件代码已经执行”。这两个证据合在一起，说明 `--patch insert` 把本地插件装进了 Cordis runtime，并且影响到了宿主执行和模型上下文。

## 这次实践留下的证据

| 架构点 | 实践证据 |
| --- | --- |
| profile 能切换运行形态 | `headless` 和 Web UI 分别可用 |
| tool registry 参与真实行动 | Web UI 任务发生读文件、改文件、跑测试；工具管线由 `dsh-tools` 定义。[5] |
| session/event 支撑观察 | Web UI 展示工具过程和任务状态 |
| system prompt 可由插件贡献 | 本地插件注入 marker 后模型可见 |
| patch overlay 扩展插件树 | `--patch insert` 加载树外 ESM 插件 |
| trust fence 影响部署 | 错误反代触发 `host.listDirectory` 403 |

这次实践的价值在闭环：Harness 把 Web UI、workspace、工具、测试、插件和 prompt 组织到同一条 runtime 路径里。[4][5][6][7][8]

## 复现建议

按这个顺序来：

1. 确认 Node 和包版本：记录 `node -v` 和 `npm view @deepseek-ai/dsh version`。
2. 给 Harness 单独的 home、npm cache 和 workspace。
3. 先跑 headless smoke，把 provider、profile 和 agent loop 验掉。
4. 启动 Web UI 时先监听本机或受控内网；需要公网入口时按敏感服务反代。
5. 准备一个小仓库任务：文件少、有测试、bug 可定位、无敏感数据、允许 agent 修改、能从测试和文件回读。
6. 再试插件：第一个插件只做 prompt section 或只读工具，先验证 loader、生命周期和模型上下文。

## 安全边界

DeepSeek Harness 可以让模型读文件、改文件、跑命令、调用工具。部署时至少满足这些要求：Web 入口有访问控制；workspace 限制在受控目录；公开文章不贴真实服务入口；截图和日志不暴露密钥、内部路径、内部主机名；高风险工具走审批或 sandbox；未授权用户无法直接访问 host API。

学习和评估阶段，最好放在本机或内网，用受控示例仓库。

## 结论

DeepSeek Harness 现在是 developer preview，版本、插件路径、Node 环境和反代 trust 都可能踩坑。它已经跑通一条可研究的 runtime 路线：Web UI、headless CLI、profile/bundle/patch、Cordis 插件树、system prompt assembly 和工具执行管线可以组合在一起。

对想研究 agent 平台的人，它比封闭 CLI 更适合拆解。你能看到模型上下文、工具执行、事件记录和扩展点怎样连接成一套 runtime。
