DeepSeek Harness 上手读法：从 dsh、profile、plugin 到 Cordis

2026年8月14日 · 阅读需 12 分钟

DeepSeek Harness 刚发布时，最容易被看见的是 Web UI：打开页面、选模型、发任务。那只是入口。更值得拆开的，是它怎样把一个 agent runtime 拼起来：dsh 负责启动，profile 决定装配，bundle 带来成组能力，patch 改变插件树，Cordis 负责插件生命周期，session/event 留下模型可见内容和工具执行痕迹。

我这次没有只停在页面能打开，而是按 quick start 到实践闭环跑了一遍：先让 npm 包在隔离 Node 运行时里启动，再用 headless 做最小 smoke；随后通过 Web UI 加 workspace，让它修一个有测试的小仓库；中间排过一次 workspace API 403；最后再写一个最小 Cordis 插件，用 --patch 插进 headless profile，验证宿主侧和模型侧都能看到 marker。

这组过程比一张最终截图有用。它能回答一个更具体的问题：DeepSeek Harness 到底是普通聊天网页，还是已经把模型、工具、文件系统、权限、session、插件这些部件拆成了可观察、可替换的运行时结构。

先把对象摆正：dsh 是装配入口​

官方 README 给出的最快入口是 npx @deepseek-ai/dsh web，默认服务在 127.0.0.1:3080。这条命令很短，背后不是“启动一个前端页面”这么简单。dsh web 会选择 Web 相关 profile/bundle，把模型 provider、工具、session、workspace、settings、client UI 等插件装进同一棵 Cordis plugin tree。

同一个 dsh 还可以跑 headless：dsh --profile headless "..."。它不打开浏览器，而是执行一轮任务后退出。Web UI 和 headless 的关系，不是两个互不相干的程序，而是同一套 runtime 在不同入口下加载了不同的能力组合。

profile 也不是普通偏好设置。官方文档里，一个 profile 目录通常会包含 package.json 和 cordis.patch.yml。package.json 记录树外依赖和 dsh.profile.bundles，cordis.patch.yml 是这个 profile 自己的 patch layer。运行时从空 root 开始，先加载 bundle patch，再加载 profile patch，再加载 $DSH_HOME/cordis.patch.yml，最后叠命令行传进来的 --patch。这个顺序决定了哪个能力先注册，哪个插件可以覆盖或插入运行时。

把这些词串起来，DeepSeek Harness 的读法就清楚了：dsh 是 launcher，profile 是运行时装配方案，bundle 是可复用能力包，patch 是改装层，Cordis plugin tree 是实际被激活的能力图。Web UI 只是其中一个入口。

Quick start 不是截图，而是一串验收点​

我在实践机上没有改系统 Node，而是在隔离运行目录里使用符合要求的 Node。最终跑通的组合是 Node v22.19.0 和 @deepseek-ai/dsh@0.1.0-rc.6。Node v24.x 路线曾因为 node-pty rebuild 需要更高 C++ 标准而失败，后面改用 Node 22.19.0。

quick start 的验收顺序如下：先确认 Node 版本，再安装 npm 包，启动 dsh web，用 HTTP 回读页面启动标记，最后跑一次 headless 最小任务。headless 那一步很重要，它能排除“网页壳能打开，但 profile/provider/凭据/模型请求链路没通”的情况。

这一步不评价 agent 编码能力，只检查运行时底座是否站住。agent 系统里很多后续问题，最后会落回很基础的几件事：profile 是否初始化，provider 是否可用，凭据有没有被安全加载，workspace 入口有没有边界，Web UI 和 headless 是否指向同一套运行时状态。

Web UI 实践：让它修一个能验收的小仓库​

页面打开后，我没有直接用长项目测试，而是准备了一个很小的 Node.js 仓库。仓库里有 package.json、src/quote.js、test/quote.test.js，其中 discountPercent 被故意写错：传入 10 本来表示 10%，bug 版本却把它当成原始乘数。

给 Harness 的任务也很明确：先读项目文件，理解测试失败原因，修复 estimateQuote 的百分比计算逻辑，运行 npm test，再写一个 PRACTICE_RESULT.md 记录改动、原因和测试输出。这个任务很小，但覆盖了 coding agent 的几个必要动作：读文件、定位 bug、编辑代码、执行测试、写产物、回读结果。

下面是实践时回读的 DeepSeek Harness Web UI。页面已经进入中文会话界面，左侧能看到 webui-workspace，也留下了那次“修复百分比计算逻辑”的会话；中间是新会话输入框、Workspace Write 权限和模型选择。截图刻意不放地址栏、机器名、内网地址、绝对路径和凭据。

Web UI 里观察到的工具链是：注入上下文，读取 package.json，读取 src/quote.js，读取 test/quote.test.js，编辑 src/quote.js，执行 npm test，写入 PRACTICE_RESULT.md，再做最终回读。服务端回读确认两个测试都通过，结果文件也存在。

这类实践比“模型最后说修好了”更能说明问题。agent 输出的自然语言报告只能算一个线索；真实文件改动、测试命令退出、结果文件内容、session 中的工具调用链，合在一起才说明这轮任务闭合了。

部署实践里卡住的不是页面，而是 workspace API​

Web UI 首次打开并不等于部署完成。我遇到的第一个实际卡点是：页面可以加载，但点击添加 workspace 时，/api/host.listDirectory 返回 HTTP 403。

这个错误暴露出 Harness 的边界设计。浏览器请求会带 Origin，后端 API 又会看到反代传入的 Host。当 public edge 把 Host 改写成另一侧的本地 authority，而浏览器 Origin 仍是公开 authority 时，Harness 的 trust fence 会拒绝目录枚举。这个行为并不坏；它阻止的是跨边界的 workspace 访问。

最后的修复不是绕过 403，而是在 public edge 上为对应入口加精确 vhost，保留浏览器请求的 Host。修好后，带 Origin 的 /api/host.listDirectory 返回 HTTP 200，Web UI 目录选择器恢复正常。

这一步改变了我对“部署 Harness”的判断标准。它不是一个静态网页服务。Web UI 背后有文件系统、shell、workspace 权限和模型工具调用。要把它放到服务器入口上，必须同时验证页面、API、Host/Origin、workspace 边界和停止/日志方式。

插件实践：证明它进入了运行时，而不是只在目录里​

DeepSeek Harness 反复强调 “Everything is a Plugin”。这句话要落到实践里，不能只看目录里有没有 package，也不能只看文档说支持插件。我写了一个最小 Cordis 插件，通过 --patch 插入 headless profile。

插件做两件很小的事。第一，在 apply(ctx) 被调用时写出 marker，证明宿主侧确实加载了插件。第二，通过 ctx.systemPrompt.section() 注入一段提示，让模型路径能返回 DSH_PRACTICE_PLUGIN_ACTIVE。最后再在运行日志里留下 PLUGIN_EXTENSION_VERIFIED=1。

这轮也遇到两个细节。第一次用相对路径加载树外插件失败，因为 loader 不是从 overlay 文件所在目录解析模块，而是按 profile 侧的解析规则走；改成绝对 file:// 后才进入插件树。第二次 headless 单独运行时缺 provider 环境，后面改为复用 Web 启动时的安全加载方式，只检查 present，不打印任何密钥值。

这两个坑反过来说明 --patch 的位置很重要。patch 文件不是“把 YAML 放在旁边就能加载”，它贡献的是运行时配置；模块路径、provider 环境、profile 选择、Cordis 依赖等待，都在同一套装配规则里。

一轮 turn 的结构，比页面样子更值得看​

官方架构文档里有一条 turn flow。一次 turn 从 turn/start 开始，运行时 claim 下一条输入，拼 prompt section 和 tool schema，进入 agent/pre-step。step 开始后，用户消息写进 log，运行时从 session log 推导模型历史，发起 agent/request，接收 llm/stream，生成 assistant chunk 和 assistant message。模型调用工具时，会经过 tools/pre-execute、tools/execute、tools/post-execute，工具结果再回到 session。step 结束后，turn stopping 决定是否继续。

这条链路把 agent 行动拆成很多可观察点。session/event 尤其值得盯。文档里的原则是：model-visible means logged。只要进入模型请求的内容，就应该能从 log 重建。agent 出问题时，最终回答经常帮不上忙。你需要知道 prompt 里有没有某段上下文，工具 schema 是哪个版本，审批策略有没有拦命令，provider streaming 中间有没有 partial，UI 渲染结果是否漏掉 session 里的事实。

agent/pre-step、agent/request 和工具管线也说明，插件的层级高于“新增一个工具按钮”。插件可以参与 prompt assembly，可以影响 claimed messages，可以接入模型请求，可以挂工具执行前后的阶段。Harness 暴露的是 runtime seam：prompt、LLM、tool、session、workspace、sandbox、provider。接入这些位置能带来扩展能力，也会带来权限和可追踪性责任。

Cordis 给 Harness 的插件系统提供语言​

DeepSeek Harness README 指向 Cordis 和论文《A Programming Paradigm for Spatiotemporal Composability》。读 Harness 时，Cordis 最有用的地方不是形式化符号，而是给了两个检查插件系统的词：temporal composability 和 spatial composability。

Temporal composability 关心时间。一个插件注册 tool、监听事件、添加 prompt section、打开连接或挂 UI node，卸载时这些影响应该能撤回。对应到 agent runtime，工具、prompt、session hook、provider adapter、审批策略不能在 profile 切换或插件卸载后继续残留。

Spatial composability 关心依赖空间。一个插件可能依赖模型 provider，另一个依赖 workspace provider，还有一个依赖 shell backend 或 sandbox policy。依赖不能只靠启动顺序和全局变量默契维持。运行时要知道谁依赖谁，谁可以激活，谁应该等待，依赖变化时谁需要停用或重接线。

Cordis 论文里的 revertible effects 和 reactive coeffects，正好解释 Harness 为什么要把 profile、bundle、patch、plugin tree 放到前台。revertible effects 让 runtime 能跟踪并撤销插件产生的影响；reactive coeffects 让组件根据上下文依赖进入 activating、deactivating 或 neutral。放回 Harness，就是工具注册在哪里、provider 谁提供、workspace 权限从哪里来、session hook 怎么撤、profile 切换是否干净。

要谨慎的是，Cordis 论文不能替代 Harness 实测，也不能证明 Harness 已经稳定。更合适的用法，是拿 Cordis 这套语言检查 Harness：effect 能否撤销，coeffect 能否声明，profile 切换是否干净，plugin reload 后有没有残留，session/event 能否把模型可见内容留下来，sandbox 和 workspace provider 是否有清楚边界。

我现在会怎么判断它​

DeepSeek Harness 目前更适合两类用途：研究 agent runtime，以及在受控环境里做插件、profile、workspace 实验。它还不适合被当成成熟的公网 coding agent 服务直接扔给团队。官方自己也标着 developer preview，并提醒会有 breaking changes。

只想尝鲜时，dsh web 很快能打开。但有价值的上手路径应该长一点：读 docs/architecture.md，看 turn flow、session log、prompt assembly、tool pipeline、provider seam 和 sandbox；跑 headless 最小 smoke；准备一个小仓库让 Web UI 做可回读修改和测试；再写一个 marker 插件，用 --patch 证明它进入宿主和模型路径。这样跑完，看到的是 runtime 结构，不只是聊天页面。

我不会把它说成可以马上替代现有 IDE agent。它现在更像 DeepSeek 把 agent runtime 的一部分设计公开出来：模型调用之外，还有 session 如何记录，工具如何执行，插件如何接线，workspace 如何隔离，运行时如何由 profile 和 bundle 拼出来。

AI 编程工具继续往前走，差异不会只在模型强弱。长期使用时，工程问题会越来越具体：一次错误工具调用怎么追踪，插件怎么升级，workspace 权限怎么收口，团队 profile 怎么复用，session 怎样回放，模型上下文怎样解释。DeepSeek Harness 还早，但它把这些问题放到了运行时层面。
