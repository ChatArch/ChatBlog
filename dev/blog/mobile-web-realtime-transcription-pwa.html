网页按钮实时录音转写：主流开源与官方方案怎么选

2026年8月8日 · 阅读需 9 分钟

先纠正前一版：我不应该把问题先扩成“找一个完整手机 PWA 会议笔记产品”，然后把一堆低星 demo 放进主表。这个需求其实更简单，也更常见：部署一个网页，用户打开页面，点击录音按钮，浏览器麦克风开始采集，页面实时显示他说的话；停止后，把 transcript 交给 LLM 生成会议笔记、想法笔记或行动项。

这不是 meeting bot，不需要自动加入 Zoom / Teams / Google Meet；也不是桌面系统音频管道。核心只有两步：

网页录音按钮 -> 实时 speech-to-text 字幕 -> AI 笔记/归档
同主题前情
  • 录音转写与会议笔记自建选型：Vexa、Scriberr、Whishper 与 Whisper 底座：那篇是大地图，覆盖 meeting bot、录音文件后台、字幕工具和本地 ASR 底座。

本文重写后只看一个更窄、更实际的入口：网页上一颗录音按钮，实时出字幕。

一句话结论

如果要最快做出靠谱 MVP，优先看 Deepgram 官方 Next.js Live Transcription starter 或 AssemblyAI 官方 browser realtime WebSocket 示例。如果要 OpenAI 生态，参考 openai-realtime-console；如果偏企业云/中文可控，参考 Azure Speech SDK JS / Azure Samples；如果只做浏览器原型，可以用 react-speech-recognition / Web Speech API；如果必须自托管 ASR，再看 WhisperLive。

证据口径

本文快照日期为 2026-08-08。主表只放主流 SDK、官方 starter、官方 sample 或高星项目；不再把零星个人 demo 当候选主线。Stars 是 GitHub API 当日快照，只用来判断项目是否属于主流参考，不作为唯一质量指标。

原创架构图：一颗网页录音按钮到实时字幕，再到 AI 笔记。重点是成熟 ASR streaming SDK / 官方 starter，而不是 meeting bot 或低星 demo。

需求重新定位​

你要的不是“会议系统”，而是一个普通网页：

  1. 用户打开一个 URL；
  2. 点“开始录音”；
  3. 浏览器请求麦克风权限；
  4. 前端用 getUserMedia / MediaRecorder / AudioWorklet 采集音频；
  5. 音频实时送到 ASR；
  6. 页面不断显示 partial / final transcript；
  7. 停止后，把 transcript 交给 LLM 做会议笔记、想法笔记、行动项和归档。

所以选型不应该先找“完整会议笔记 SaaS 的开源替代品”。正确问题是：哪条成熟实时 ASR Web 路线最容易部署成我们自己的网页？

如果只选一个开始，我会选 Deepgram Next.js Live Transcription；如果 Deepgram 不适合中文/成本/合规，再平移到 Azure Speech SDK 或国内云 ASR，但网页形态仍然是一样的。

为什么 Deepgram / AssemblyAI 这类官方 starter 更对题​

你要的是一颗按钮，不是一个大平台。Deepgram 和 AssemblyAI 的官方 starter 正好给了最小闭环：

Browser microphone
  -> WebSocket / live transcription SDK
  -> partial transcript on screen
  -> final transcript segments

这类 starter 的价值不是 stars 特别高，而是：

  • 它们是 ASR provider 官方维护或官方示例；
  • API 本来就是实时转写；
  • 前端交互就是网页麦克风 + 实时字幕；
  • 代码量通常不大，容易改成自己的页面；
  • 后面接 AI notes 很自然：把 final transcript segments 存起来，停止录音后调用 LLM。

这比拿一个“会议笔记全家桶”硬改成实时网页录音靠谱，也比把零星个人 demo 放进主表靠谱。

推荐实现形态​

实际产品可以非常薄：

Web page
  - Start / Stop recording button
  - live transcript area
  - final transcript list
  - note template selector

Backend
  - create ephemeral ASR token / session
  - never expose provider API key to browser
  - receive final transcript segments
  - call LLM to generate notes after stop

ASR provider
  - Deepgram / AssemblyAI / Azure / OpenAI / Amazon / 国内云
  - returns partial + final transcript events

第一版甚至不必做复杂录音库。先把“点按钮实时出字”做稳，再做后续：保存录音、保存 transcript、AI 纪要、搜索、导出飞书/Markdown。

Provider 怎么选​

场景首选
最快网页 MVPDeepgram Next.js live transcription starter
想看最小浏览器 WebSocket 代码AssemblyAI browser JS realtime example
已经决定 OpenAI 生态，想把实时语音和 LLM 放一起OpenAI Realtime Console / Realtime API
企业云、中文、多语言、稳定 SDKAzure Speech SDK JS / Azure Samples
AWS 体系内Amazon Transcribe WebSocket sample 作为协议参考
内部演示、无需后端react-speech-recognition / Web Speech API
不想依赖外部 ASR，愿意维护模型WhisperLive

国内云如讯飞、腾讯云、DashScope 也可以接，但它们更像 provider adapter，不一定有同样好用的开源 Web starter。架构上仍然一样：浏览器采集音频，后端保管 key 和签名，前端只拿临时 session 或连接地址。

不再主推哪些东西​

前一版把一些低星或个人 vibe-coding 项目放进主表，这是不对的。它们可以作为灵感，但不应该成为选型结论。

这次主线不再放：

  • 只有零星 stars 的个人 demo；
  • meeting bot：Vexa、Attendee、Recall、MeetingBaaS 这类自动入会方案；
  • 桌面系统音频/全天候记录：screenpipe、Pikabaka 这类；
  • 录音文件后台：OpenTranscribe、Scriberr、Whishper 这类，它们适合上传/归档，不是“一颗网页按钮实时字幕”的第一步；
  • 完整本地模型链路：除非我们决定自托管 ASR，否则 Whisper/faster-whisper 系列只作为备选底座。

最小落地顺序​

我建议按这个顺序做：

  1. 先 fork / 参考 Deepgram Next.js Live Transcription，跑通网页按钮实时字幕。
  2. 增加后端 token broker，避免前端暴露 API key。
  3. 把 transcript event 标准化成：
type TranscriptEvent =
  | { type: 'partial'; text: string; startMs?: number; endMs?: number }
  | { type: 'final'; text: string; startMs?: number; endMs?: number }
  | { type: 'error'; message: string }
  1. 停止录音后，把 final segments 合并，调用 LLM 生成会议纪要。
  2. 再换第二个 provider，比如 Azure 或国内 ASR，验证 provider adapter 是否可替换。
  3. 最后才做录音库、权限、搜索、飞书/Markdown 导出。

最终判断​

这类项目当然有，而且很多年前就成熟了。只是它成熟的形态通常不是“一个完整开源会议笔记产品”，而是成熟 ASR 厂商的实时 Web SDK / 官方 starter。

如果要我给一个最短答案：

先用 Deepgram 官方 Next.js Live Transcription 做第一版网页实时字幕；备选 AssemblyAI browser realtime example。产品层自己做一张网页和一个 token/notes 后端。需要企业云或中文稳定性时，再换 Azure Speech SDK 或国内 ASR provider。

这才是“部署一个网页，点录音，实时显示文字，后面接 AI 笔记”的正路。
