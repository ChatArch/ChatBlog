读 Cordis 论文：DeepSeek Harness 为什么把 everything 做成 plugin

2026年8月14日 · 阅读需 10 分钟

设想一个长任务 agent 正在运行。它临时装了一个新工具，替换了 memory provider，增加了权限检查，又把 system prompt 的某一段热更新掉。旧工具注册的事件监听怎样撤？依赖旧 provider 的组件怎样重接线？新插件加载失败时，runtime 怎样回到稳定状态？

Cordis 论文 A Programming Paradigm for Spatiotemporal Composability 讨论的就是这类问题。DeepSeek Harness README 把它放在 Everything is a Plugin 旁边，是在提示一条运行时约束：agent runtime 需要一套能安装、撤销、重连组件的运行模型。[1][2][3]

这张图有两个方向：时间轴讲 effect 怎样留下撤销路径，空间轴讲依赖怎样被 runtime 看见。fiber 是两者交汇处：一个插件实例在当前 context 里安装能力、声明依赖、接受生命周期管理。右侧列的是 DeepSeek Harness 里会受到影响的 surfaces：profile/bundle/patch、prompt sections、tool registry、session event、Web UI、sandbox 和 approval。

论文要解决的运行时一致性问题​

一个组件加入系统后会做两件事：改变共享环境，也依赖共享环境。事件监听、service provider、prompt section、工具 schema、UI projection、权限 guard 都属于“改变环境”；tools service、session service、模型 provider、workspace context 都可能成为“依赖环境”。

组件卸载、热更新或依赖变化时，runtime 要维持一致性。论文把这个目标拆成两类 composability：[3]

方向论文术语工程含义Agent runtime 里的例子
时间temporal composability组件安装的能力有撤销路径tool、listener、prompt section 随插件卸载而撤销
空间spatial composability组件依赖由 runtime 声明、解析和重连provider 变化后，consumer 重新激活或卸载

这个拆分很适合看 DeepSeek Harness。它的工具、prompt、session、UI、guard、sandbox 都会进入运行时，而这些能力的生效和撤销都不该靠“作者记得清理”。

Temporal：安装能力时留下撤销路径​

论文把 temporal composability 建模成 revertible effects。简化后可以这样理解：一次 context 修改会产生新的 context，也会交出一个 inverse。runtime 后续可以按顺序调用这些 inverse，把组件安装过的能力撤掉。[3]

普通插件系统常把生命周期拆成 activate() 和 deactivate()。作者在 activate() 里注册东西，再在 deactivate() 里手写清理。Cordis 的做法更紧：注册动作本身带 disposer。注册 listener，runtime 拿到取消监听的函数；提供 service，runtime 拿到撤销 provider 的函数；一个 fiber 下累积多个 disposer，卸载时按 LIFO 顺序恢复。[3]

DeepSeek Harness 的扩展点沿着这条路设计。官方架构文档和 extension cookbook 把工具插件、hook 插件、UI 插件、protocol driver 放在 Cordis context、service、events 和 fiber lifecycle 里。[1][7][8]

对 agent runtime 来说，清理不干净会直接改变模型行为。permission hook 残留会影响下一次工具调用；tool schema 残留会让模型看到过期能力；prompt section 残留会污染后续 turn。Temporal composability 给这些问题一个检查标准：能力安装时，撤销路径也要进入 runtime。

Spatial：依赖关系交给 runtime 管​

Spatial composability 关注组件需要什么环境。论文使用 coeffect 描述这种“运行前提”：组件声明依赖，runtime 检查 context 是否满足；依赖满足时激活，依赖消失时停用或重接线。[3]

论文里有三种依赖状态，改成工程语言就是：

状态含义运行时动作
activating原来缺依赖，现在依赖出现加载或恢复组件
deactivating原来依赖满足，现在依赖消失卸载组件并撤销 effects
neutral依赖满足情况没有变化保持现状

放到 Harness 的插件树里，工具通过 registry 进入执行管线，system prompt section 进入模型上下文，UI 插件监听 session event。依赖写在 README 里只能提醒人；依赖交给 runtime，系统才能排序、重连和撤销。[5][6][8]

Cordis 对 agent harness 的价值在这里变得具体：插件化能力变成运行时可见的依赖图。runtime 能看到哪个 fiber 提供 provider，哪个 fiber 消费 provider，配置或 provider 变化后应该动哪些组件。

Fiber：插件实例是运行中的组件​

论文把 component 的运行实例称为 fiber。一个 fiber 有自己的 context、依赖声明、已安装 effects、提供的能力和生命周期状态。[3]

在 Harness 里，一个 npm package 只是代码。profile、bundle、patch 启动后，被加载出来的 plugin instance 才会影响系统。它挂在插件树里，贡献 service、event listener、prompt section 或 tool definition，也接受依赖变化和卸载流程管理。[1][4]

这个视角能串起前两篇实践里的几个现象：

Harness 现象Fiber 视角
profile / bundle / patch决定当前插件树长什么样
ctx.systemPrompt.section()当前 fiber 向模型上下文贡献 section
ctx.tools.register()当前 fiber 向工具 registry 注册能力
session/eventUI 和 replay 订阅 runtime 事实
--patch insert把树外插件实例装进当前 runtime

这个视角比“扩展点回调”更具体。插件实例会进入 lifecycle，安装的 effects 由 runtime 追踪，声明的 coeffects 由 runtime 检查。

Agent harness 为什么特别需要这套模型​

论文在动机里直接提到 self-evolving agent harnesses。现代 agent harness 会组合 tool suites、execution environments、permission / sandboxing、session persistence、context management、memory、subagents 和 UI；未来还可能生成并部署自己的组件修改。[3]

这类系统把很多高权限能力绑在一起：模型上下文、工具 schema、文件系统、shell/subprocess、Web/MCP/subagent、session state、approval/guard、UI projection。能力越多，动态组合的风险越大。

几个场景可以说明 Cordis 模型的用处：

场景runtime 需要保证什么
新 tool provider 加入模型看到的 tool schema 随当前 registry 更新
permission 插件卸载guard、listener 和残留状态一起撤销
provider 替换依赖旧 provider 的组件重新解析或停用
Web UI 热更新session stream 和 host API 保持一致状态
不可信插件接入插件在 sandbox 或 bridge context 里拿到被削弱的能力

论文第 6 节对系统边界讲得很谨慎：语言层 access control 挡不住恶意代码直接触达 host runtime；不可信组件需要放进单独 sandbox、进程或虚拟化边界，再通过 bridge 获取有限能力。[3]

这能解释 DeepSeek Harness 的部署口径。Web UI 背后连接 workspace、文件系统、shell 和工具执行。反代、认证、Host / Origin trust fence、sandbox 和 approval 都会改变 runtime 的真实安全边界。[1][7]

三个能带回工程实践的判断​

第一，插件作者要把资源获取和释放放在同一个局部结构里。ctx.effect() 让 runtime 收集 disposer，清理逻辑不再散落在多个生命周期函数里。[3]

第二，依赖访问要经过 runtime。ctx.set(key, value)、ctx.get(key)、isolation、interception、proxy-mediated property access 的成本更高，但 runtime 因此能知道 fiber 依赖什么、当前 provider 是谁、变化时该刷新谁。[3]

第三，配置变更要走 reconciliation。论文实现部分讨论 declarative configuration 和 HMR：entry 记录 id、url、isolate、intercept、config、disabled；loader 用 reconciliation key 调整 fiber；HMR dispose 旧 fiber、import 新模块，失败时恢复 cache。[3] Harness 的 profile / bundle / patch 也可以放在这个视角下理解：它们描述一棵可协调的插件树，远比普通 CLI 参数集合更接近运行拓扑。[4]

前一篇实践里用 --patch 加载本地 Cordis 插件，再通过 ctx.systemPrompt.section() 注入 marker，本质上就是验证这条路线：树外插件能进入 runtime，并影响模型上下文。[4][6]

论文留下的边界​

这篇论文给的是运行模型，完整安全产品还需要部署层、权限层和 sandbox 配合。有三处边界要记住。

  1. Revertible effects 依赖插件给出正确 inverse。Cordis 可以追踪 disposer、按顺序调用 disposer，但它无法自动证明 disposer 真能撤回 effect。论文也提到 runtime 没有检查 witnessed refinement 里的证明义务。[3] 放到 Harness 里，工具插件撤销注册容易检查；已经写进用户仓库的 diff，需要额外的确认、回滚或审计机制。
  2. 外部副作用需要单独处理。打开资源、注册 listener 适合 tracked disposer；向外部 API 发请求、写用户仓库、发送消息这类 emission 通常只能延迟提交、显式确认或补偿。[3] 对 agent 平台来说，approval 决定外部副作用在哪个时刻提交。
  3. Dependency typing and versioning 仍是开放问题。论文第 6.6 节专门讨论这个问题：只靠 key identity 解决不了 interface drift 和 key collision。[3] Harness 插件生态里的 tool schema、credentials provider shape、UI event payload 都需要 namespacing、schema check、manifest 或 capability negotiation。依赖名称对上，只能说明找到了 provider；协议是否兼容，还需要另一层约束。

回看 DeepSeek Harness​

前两篇文章分别讲了 Harness runtime 架构和一次部署/插件实践：

  • DeepSeek Harness 是什么：把模型接进 workspace 的 Agent Runtime
  • DeepSeek Harness 实战：部署、修 bug、加载一个本地插件

Cordis 论文给这些实践补上设计语言。DeepSeek Harness 把 everything 做成 plugin，是因为工具、prompt、session、UI、provider、guard、sandbox 都可能在运行中出现、消失、替换、拦截和重组。

看一个 agent runtime 时，可以用四个问题检查它的底座：

检查问题对应 Cordis 概念
组件安装的能力能撤回吗？revertible effects
组件依赖谁，runtime 看得见吗？reactive coeffects
插件实例有生命周期归属吗？fiber
不可信组件和外部副作用在哪里越界？system boundary / sandbox

我对 Harness 的判断也更清晰：它适合研究现代 coding agent runtime 的拆法；它仍处在 developer preview；安全边界要靠部署层认证、权限策略和 sandbox 一起完成。回到上面的四项检查：effect 能撤回，coeffect 可见，fiber 有生命周期归属，不可信组件和外部副作用有明确边界。
